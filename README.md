# StasyClean — сайт клининговой компании

Статический сайт для клининговой службы в Белграде: три языка (сербский,
английский, русский), демонстрационный стенд для выбора стиля и готовая
прод-сборка для nginx.

- **Прод**: `https://stasyclean.com` — набор HTML, CSS и минимального JS
- **Демо-стенд**: GitHub Pages, с панелью настроек, которая позволяет
  заказчику переключать темы, палитры внутри темы, акцент, шрифт, плотность,
  фон, текстуру и декор прямо в браузере

## Быстрый старт

```bash
npm ci
node scripts/sync-fonts.mjs   # разложить шрифты из Fontsource в src/assets

npm run dev                   # локальная разработка с демо-панелью
npm run build:demo            # демо-стенд → dist-demo/ (base=/stasyclean)
npm run build:prod            # прод-сборка → dist/     (base=/)
npm run serve:prod            # посмотреть прод-сборку на localhost:8080
```

## Два режима сборки из одного исходника

| | `build:prod` | `build:demo` |
|---|---|---|
| Каталог | `dist/` | `dist-demo/` |
| Базовый путь | `/` | `/stasyclean/` |
| Домен в метатегах | `stasyclean.com` | `pglyan.github.io` |
| Панель настроек | нет | есть |
| `robots.txt` | индексация открыта | `Disallow: /` |

Режим задаётся переменной `PUBLIC_DEMO=on`. Её видит и конфиг
(`process.env`), и компоненты (`import.meta.env.PUBLIC_DEMO`, дополнительно
через `.env.demo`). Прод-сборку нельзя случайно собрать с включённой
панелью, а демо — с открытой индексацией.

## Команды проверки

```bash
npm run check              # типы: astro check + TypeScript по всем .astro/.ts
npm run check:colors       # контраст всех тем и палитр + свотчи паспорта + запрет литеральных цветов
npm run check:i18n         # 39 страниц: переводы, ссылки и метатеги ведут на существующие файлы
npm run check:i18n:demo    # то же для демо-сборки (base=/stasyclean/)
npm run check:size         # бюджеты в gzip: страница ≤16 КБ, CSS ≤12 КБ, шрифт ≤40 КБ, OG ≤80 КБ
npm run check:clean        # в prod-сборке только выбранная тема, её палитры и ни одного следа панели
npm run check:clean:demo   # зеркально: в демо-стенде есть все темы, палитры и сама панель
npm run check:mobile       # браузер: нет горизонтального скролла, цели ≥44px, поля ≥16px
npm run check:mobile:demo  # то же для демо-сборки (base=/stasyclean/)
npm run make:og            # пересобрать OG-картинки → public/og/{sr,en,ru}.png
```

Проверки `check:i18n`, `check:size`, `check:clean` и `check:colors`
выполняются в CI перед публикацией демо-стенда
(`.github/workflows/deploy-demo.yml`), поэтому сломанный перевод, битая ссылка,
распухшая страница, пропавшая из стенда тема или палитра, нечитаемый оттенок
или разъехавшийся свотч не доедут до заказчика. `npm run check` (типы) и
`npm run check:clean` (чистота прод-сборки) запускаются локально перед коммитом.

`check:mobile` — единственная проверка, которой нужен настоящий браузер.
Playwright намеренно **не** входит в зависимости проекта: это ~150 МБ и минуты
CI, а проверка нужна перед выкладкой, а не на каждой сборке. Один раз:

```bash
npm i -D playwright && npx playwright install chromium
npm run check:mobile
```

Скрипт ищет браузер в трёх местах (переменная `PLAYWRIGHT_DIR`, обычное
разрешение модуля, кэш `npx`) и, если не находит, объясняет, что установить.

## Демо-стенд на GitHub Pages

Стенд открыт по адресу **https://pglyan.github.io/stasyclean/** и обновляется
сам: push в `main` запускает `.github/workflows/deploy-demo.yml`, вручную —
кнопка Run workflow (`workflow_dispatch`).

Пайплайн повторяет «Быстрый старт» и добавляет публикацию:

| Шаг CI | Зачем |
|---|---|
| `npm ci` | установка строго по lock-файлу |
| `node scripts/sync-fonts.mjs` | файлы `.woff2` в git не лежат (см. `.gitignore`), их копируют из пакетов Fontsource |
| `npm run build:demo` | сборка стенда: `PUBLIC_DEMO=on`, `base=/stasyclean`, панель включена |
| четыре проверки | i18n, бюджеты, полнота стенда, контраст |
| `upload-pages-artifact` → `deploy-pages` | публикация каталога `dist-demo` артефактом |

Почему артефактом, а не веткой `gh-pages`: при публикации артефактом GitHub
отдаёт файлы как есть, без обработки Jekyll, поэтому каталог ассетов `_a/`
не «съедается» служебным правилом Jekyll, а сгенерированный `404.html`
работает штатно.

Разовая настройка репозитория — источник Pages «GitHub Actions»:

```bash
# то же самое, что Settings → Pages → Source: GitHub Actions
gh api -X POST repos/pglyan/stasyclean/pages -f build_type=workflow
gh api repos/pglyan/stasyclean/pages --jq '{build_type, html_url}'   # проверка
```

Если Pages не включить, шаг `configure-pages` в CI упадёт с подсказкой:
он не создаёт сайт сам, а только готовит сборку к публикации.

Адрес стенда и базовый путь связаны жёстко и меняются только вместе:

| Что | Значение | Где задано |
|---|---|---|
| Адрес | `https://pglyan.github.io/stasyclean/` | `DEMO_ORIGIN` в `astro.config.mjs` |
| Базовый путь | `/stasyclean/` | `DEMO_BASE` там же |

`/stasyclean` — это имя репозитория: GitHub Pages отдаёт project-сайт из
подпапки с его именем. Переименовали репозиторий — поправьте обе константы,
иначе ссылки, шрифты и ассеты разъедутся с адресом.

Демо-стенд закрыт от индексации: `robots.txt` в демо-сборке отдаёт
`Disallow: /`, поэтому презентационная версия не конкурирует с рабочим сайтом.
Выкладка боевой версии на nginx — `deploy/README.md`.

```
├─ components/      секции страниц, обвязка, демо-панель
├─ layouts/Base.astro
└─ pages/           маршруты (по файлу на тип страницы)
deploy/             конфиг nginx и инструкция по выкладке
scripts/            сборка шрифтов и OG-картинок, минификация, проверки (в т.ч. контраст, чистота сборки и мобильная вёрстка в браузере), локальный сервер
```

## Как устроены темы

Тема здесь — не палитра, а целый стиль оформления: своя типографика, форма
карточек и кнопок, ритм секций, фон страницы, текстура, декор и обработка
фотографий. В проекте таких стилей десять: `fresh` (базовая коммерческая),
`trust`, `citrus`, `sand`, `nordic`, `atelier` (журнальная подача), `mila`
(тёплая округлая), `bubble` (светлая «мыльная» с пузырьками), `sorbet`
(лилово-персиковая пастель) и `zine` (брутализм и самиздат). Три последние
милые темы образуют линию: у них общий набор механизмов (декор, текстура,
форма фото, анимации) и общие правила, см. «Правила милой линии».
Каждая тема живёт в четырёх файлах:

| Что | Где |
|---|---|
| Данные для панели и сборки | `src/data/themes.ts` |
| CSS темы: палитра, тени, декор | `src/themes/<id>/theme.css` |
| Палитры темы (цветовые наборы) | `src/themes/<id>/palettes.css` |
| Вход сборки: какие шрифты везёт | `src/themes/entries/<id>.ts` |

Добавить тему — пять шагов: написать `src/themes/<id>/theme.css` по образцу
соседней, описать `defaults` и `available` в `src/data/themes.ts`, добавить
`src/themes/entries/<id>.ts` и дописать тему в демо-входы (`src/themes/all.css`,
`src/themes/entries/all.ts`). Файл `palettes.css` нужен, только если у темы
больше одной палитры.

### Палитры

Палитра — это набор цветов одного настроения внутри темы: у «Милоты» тёплые
(`rose`, `peach`, `butter`, `lilac`), у «Голубой свежести» холодные (`sky`,
`mist`, `milk`, `aqua`), у «Сорбета» пастельные (`lilac`, `peach`, `sky`,
`butter`). Всего в трёх темах двенадцать палитр. Палитра меняет **только
цвета**: фон, подложки, чернила, акцент и цвет ссылок. Ни формы, ни шрифты, ни
плотность от неё не зависят, поэтому палитру можно переключать на живой
странице без пересборки.

Почему цвета палитры лежат в файле темы, а не в общем реестре: одна и та же
палитра в разных темах выглядит по-своему. В прод-сборку попадает
`palettes.css` только выбранной темы, и `npm run check:clean` это проверяет —
точно так же, как с `data-skin` и шрифтами. Подписи палитр (id и название на
трёх языках) лежат отдельно, в `src/data/palettes.ts`: они от темы не зависят.

Главное свойство схемы: **тема не стоит продакшену ни одного байта, пока её не
выбрали**. В прод-сборке алиасы `@skin` и `@theme` (astro.config.mjs) ведут на
CSS и вход ОДНОЙ темы, поэтому остальные девять в артефакты не попадают вовсе,
а шрифты чужих семейств даже не скачиваются. Выбор фиксируется одной командой:

```bash
npm run design                     # что выбрано сейчас и что уедет в сборку
npm run design -- list             # список доступных тем
npm run design -- set theme=mila   # выбрать тему
npm run design -- set palette=peach  # …и палитру внутри неё
npm run check:clean                # убедиться, что в dist только она
npm run check:colors               # проверить контраст всех палитр
```

Оговорка про общие механизмы: фон страницы, декор, петли анимаций и форма
фото-слота живут в общем `src/styles/params.css`, поэтому их CSS едет в каждой
прод-сборке — даже той, что ими не пользуется. Это сознательный обмен
«переиспользование против байтов»: механизм оплачивается один раз (~0,2 КБ
gzip), а не дублируется в каждой милой теме. Специфика темы (палитры, декор
именно этой темы, её правила) остаётся в её собственном CSS.

Параметры оформления (акцент, радиус, плотность, карточки, кнопки, ширина
контейнера, раскладка первого экрана, ритм секций, фон страницы, текстура,
декор, лечение и форма фото, палитра) — сквозные: значение из
`design.config.json` становится атрибутом на `<html>` (`data-card="sticker"`),
а `src/styles/params.css` превращает его в переменные. Поэтому одна и та же
разметка читается как брошюра, как журнал или как бюллетень — без второго
набора компонентов и без дублирования секций.

## Мобильная база

Сайт верстается mobile first: базовые правила пишутся без media query и
рассчитаны на 320px, а `@media (min-width: …)` только **добавляет** удобства
широким экранам. Брейкпойнтов ровно три, и они одинаковы во всех слоях:

| Ширина | Что меняется |
|---|---|
| `30rem` / 480px | кнопки первого экрана перестают растягиваться на всю ширину |
| `48rem` / 768px | в шапке возвращаются переключатель языка и кнопка Telegram, таблица цен снова становится таблицей |
| `62rem` / 992px | горизонтальное меню вместо «шторки», две колонки в сайдбарах, закреплённая панель действий скрывается |

Контракт брейкпойнтов записан в `src/styles/layout.css`, токены телефона —
в `src/styles/tokens.css`. Исключения (`max-width: 61.999rem`) ровно три, и все
они означают «только для телефона»: резерв под панель действий, отступ баннера
cookie и кнопка демо-панели.

Что именно сделано для телефона и почему:

- **Цели нажатия ≥ 44×44px и кегль полей ≥ 16px** — `components-core.css`,
  раздел «Минимумы для тач-ввода». Правило живёт в одном месте, а не в каждом
  блоке: иначе «Подробнее» в карточке услуги было 34px, переключатель языка —
  38×29px, а ссылки подвала — 21px. Шестнадцать пикселей в поле — это порог, ниже
  которого iOS Safari зумит страницу при фокусе и обратно не возвращает.
- **Шапка**: на телефоне в ней только логотип и кнопка меню, переключатель
  языка переехал в «шторку» (и остался в подвале). До этого шапка требовала
  392px при экране 320px — вся страница получала горизонтальный скролл, а
  мобильный браузер показывал её уменьшенной.
- **Панель действий снизу**: высота задана токеном `--sticky-h`, и из того же
  числа считается отступ `body`, поэтому панель не может стать выше отведённого
  ей места. Подписи кнопок короткие (`ui.cta.bookShort`), полный текст — в
  `aria-label`, а короткая форма является префиксом полной (WCAG 2.5.3).
- **Таблица цен** на телефоне становится карточками: заголовки столбцов
  переезжают в `data-label` и подставляются через `::before`. Разметка при этом
  одна на все ширины, семантику таблицы браузер сохраняет даже при
  `display: block` (проверено деревом доступности Chromium: на 360px и 1280px
  оно одинаковое). Плата за это — высота страницы: полный прайс занимает больше
  экранов, зато ни одна цена не спрятана за горизонтальным свайпом.
- **Калькулятор**: панель результата прилипает к низу экрана, пока листается
  список опций, — сумма видна сразу после нажатия на чип.
- **Кнопки первого экрана** на узких экранах занимают всю ширину: ниже ~460px
  они всё равно переносятся, и пара разной ширины выглядит случайной.
- **Подвал** — две колонки вместо одной ленты (было 1104px высоты).
- **Меню телефона**: `role="dialog"`, `aria-modal`, ловушка фокуса, возврат
  фокуса на кнопку меню, `overscroll-behavior: contain`.
- **Ховер-состояния** включаются только при `@media (hover: hover)`: на
  тач-экране браузер оставляет `:hover` после тапа, и элемент «залипает».
- **Безопасные зоны**: `viewport-fit=cover` в метатеге плюс
  `env(safe-area-inset-*)` у `body` и панели действий — на iPhone с вырезом
  контент не уходит под вырез, а кнопки не оказываются под индикатором «домой».

Проверяется это не глазами, а `npm run check:mobile`: 39 страниц × 320/360/390px,
и на каждой — отсутствие горизонтального скролла, размеры целей, кегль полей,
наложение фиксированных слоёв, резерв под панель действий, подвал под панелью и
открытое меню телефона. Комбинации оформления (десять тем и все варианты
параметров) проверяются тем же приёмом по демо-сборке.

## Правила милой линии

Темы `mila`, `bubble` (и будущие вариации) держат один характер: мягкие формы,
пастель, округлая типографика. Чтобы «милота» не превращалась в набор
случайных пятен, у линии есть короткий чек-лист — он же список того, что
проверяется машиной:

1. **Палитра — это только цвет.** Ни радиусов, ни шрифтов, ни поворотов в
   блоках `[data-palette]`. Иначе палитра начнёт спорить с параметрами темы.
2. **Никаких литеральных цветов вне блоков токенов.** В `theme.css` и
   `palettes.css` hex допустим только в блоке темы и в блоках палитр; всё
   остальное — `color-mix()` от переменных. Так смена палитры перекрашивает
   страницу целиком. Проверка: `npm run check:colors`.
3. **Контраст важнее оттенка.** Пастель легко уходит в «нечитаемо»: пороги
   `ink/bg ≥ 8`, `ink-soft` к фону и подложке `≥ 4.5`, ссылка к фону `≥ 4.6`,
   текст на заливке `≥ 4.6`. Если оттенок не проходит — меняем оттенок, а не
   порог.
4. **Светлый акцент — тёмный текст.** Если заливка пастельная, `--brand-ink`
   тёмный, а `--brand-strong` задаётся явно: производный от светлого акцента
   микс не добирает контраста для ссылок.
5. **Декор живёт под содержимым и уважает настройки.** Пузырьки и искры
   рисуются на `body::before` градиентами (ни картинок, ни JS), включаются
   только при `data-motion='on'` и выключаются при системном
   `prefers-reduced-motion: reduce`.
6. **Ни одного нового JS-файла.** Всё, что видно в милой линии, — CSS и данные.
7. **Свотч паспорта = реальный цвет.** `swatch[1]` темы и каждой палитры
   обязан совпадать с `--brand` из CSS: он показывается в панели и уходит в
   `<meta name="theme-color">`. Это тоже проверяет `npm run check:colors`.

## Как устроена мультиязычность

- Сербский (латиница) — в корне домена, английский — `/en/`, русский — `/ru/`.
  Так сделано у всех сильных конкурентов, и это даёт лучший локальный SEO.
- **Слаги переведены**, а не просто получили префикс языка:
  `/cene` ↔ `/en/prices` ↔ `/ru/ceny`. Реестр адресов — `src/i18n/routes.ts`.
- Каждый блок данных хранится в одном файле для всех трёх языков, а тип
  `Localized<T>` требует заполнить все локали. Пропустить перевод
  не даст TypeScript, а `npm run check:i18n` ловит пустые значения и
  протёкший чужой язык в собранных страницах.
- На каждой странице: `lang`, `canonical`, полный набор `hreflang`
  и `x-default`, локализованные Open Graph и JSON-LD.

## Производительность

Измерено на прод-сборке (`npm run check:size`). Общий CSS зависит от темы —
это её собственный файл плюс общий слой:

| Ресурс | Размер gzip |
|---|---|
| Внутренняя страница | 4,5–8,8 КБ |
| Главная (все блоки) | 12,9–14,6 КБ |
| Общий CSS, базовая тема `fresh` | 9,5 КБ |
| Общий CSS, самая тяжёлая тема `bubble` (Comfortaa + палитры + декор) | 10,5 КБ |
| Общий CSS демо-стенда (10 тем и 8 палитр сразу) | 14,0 КБ |
| JS на странице | около 5 КБ |
| Крупнейший файл шрифта | 36,8 КБ (Lora latin); у `bubble` — 30,1 КБ (Comfortaa) |
| Шрифты | загружаются только нужные субсеты |

Бюджет главной демо-стенда поднят с 20 до 21 КБ (`homePageDemo` в
`scripts/check-size.mjs`): русская версия стенда стояла вплотную к 20 КБ ещё до
мобильных доработок — это самая тяжёлая страница проекта, потому что кроме всех
блоков несёт разметку панели с десятью темами. Прод-бюджеты при этом не
смягчались: та же страница там занимает 14,6 КБ из 20.

Решения, которые это дают:

- **Ноль сторонних библиотек** в рантайме: только 5 небольших собственных
  скриптов (меню, табы, калькулятор, форма, панель).
- **Шрифты self-hosted** с `unicode-range`: сербская страница не тянет
  кириллицу, русская — расширенную латиницу. Предзагружается ровно один
  файл — субсет заголовков для текущего языка.
- **CSS отдельным файлом с хешем** и годовым кешем вместо инлайна:
  при 39 страницах кеш выгоднее, чем экономия одного запроса.
- **Никаких CSS-фреймворков** — 47 КБ минифицированного CSS (9,5 КБ gzip в
  базовой теме) на всю дизайн-систему с десятью темами, восемью палитрами и
  общими механизмами фона/декора. Темы не удваивают эту цифру: в прод попадает
  только выбранная (см. «Как устроены темы»), остальные девять существуют
  лишь на демо-стенде.
- **Общие механизмы дешевле копий.** Фон страницы, декор, петли анимаций и
  форма фото-слота лежат в общем слое и достаются всем темам: 8,7 → 8,8 КБ
  gzip на базовой теме при четырёх новых параметрах. Четыре палитры
  добавляют теме ~0,1 КБ каждая — дешевле, чем один лишний шрифтовой субсет.
- **Мобильный слой стоит ~0,7 КБ gzip.** Тач-минимумы 44px, кегль полей 16px,
  карточки таблицы цен, липкий итог калькулятора, две колонки подвала и
  hover-guard вместе добавили к общему CSS меньше килобайта: это те же правила
  с другими значениями, а не вторая система стилей. Дороже обошлось не
  оформление, а разметка — мобильные подписи таблицы цен и атрибуты клавиатуры
  в форме (см. бюджет главной демо-стенда выше).

## Что требуется от клиента

1. Юридические реквизиты: наименование, адрес, PIB, матични број.

3. Фотографии объектов «до и после».

5. Подтверждение районов выезда и списка услуг.
6. Проверка сербского и английского переводов носителем языка.
7. Утверждение юридических текстов юристом.
